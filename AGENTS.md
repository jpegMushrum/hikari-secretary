# Правила работы с Hikari Secretary

## Устройство проекта

- Корневой репозиторий отвечает за платформу: сведения о клубе, общую историю
  релизов, планы, развёртывание и Compose.
- `bot`, `backend`, `miniapp` — отдельные Git-сабмодули со своими инструкциями
  `AGENTS.md`. Перед изменениями прочитай инструкции соответствующего компонента.
- Backend владеет бизнес-правилами и PostgreSQL. Бот — Telegram-интерфейс
  и адаптер доставки. Miniapp использует административный API backend.
- Сохраняй существующий flow бота; miniapp дополняет его.

## Работа с изменениями

- Сначала проверь статус и diff корня и затрагиваемых сабмодулей.
  Не отменяй чужие изменения и не включай их в свою работу без необходимости.
- Делай изменения в репозитории, которому принадлежат файлы. Не подменяй
  сабмодули обычными каталогами. При разрешённом выпуске сначала публикуются
  коммиты компонентов, затем ссылки на них в корневом репозитории.
- Коммиты и push в корне и всех сабмодулях выполняет только пользователь
  после проверки изменений. Агент оставляет правки в рабочей копии.
  Для запуска развёртывания на production нужен отдельный запрос пользователя.
- Не выводи секреты из `.env`, токены и персональные данные в отчёты.
  `AGENTS.md` хранится в Git и не добавляется в `.gitignore`.
- Не удаляй Docker volumes и рабочие базы для исправления локальных ошибок.
  Не запускай доставку реальному боту ради проверки кода.
- Поддерживай два стека: `docker-compose.production.yml` и
  `docker-compose.bot-local.yml`; не создавай дублирующие Compose-файлы.

## Субагенты и модели

- Для существенных задач с независимыми частями используй субагентов.
  Небольшие локальные исправления выполняй без обязательного делегирования.
- Для документации используй `gpt-6.2-sol` с уровнем `low`.
- Для обычного ревью используй `gpt-6.2-sol` с уровнем `medium`.
- Только для сложного ревью миграций, авторизации или очередей используй `gpt-6.2-astra` с уровнем `medium`.
- Если выбранная модель недоступна, сообщи об этом и выполни задачу главным агентом. Другую модель используй только по указанию пользователя.
- Передавай каждому субагенту конкретную задачу, необходимые материалы,
  допустимые файлы, критерии готовности и ожидаемые проверки.
- Не поручай нескольким агентам одновременно редактировать одни файлы.
  Главный агент согласует изменения, проверяет результаты и отвечает за итог.
- После существенной реализации поручи субагенту ревью итогового diff:
  ошибки, регрессии, нарушения API и пробелы в тестах. Ревьюер сначала
  возвращает замечания с файлами и обоснованием, не переписывает код сам.
- Если изменились API, конфигурация или пользовательские сценарии, после
  стабилизации реализации поручи субагенту сверить и обновить документацию.
  При недоступности предпочтительной модели эти проверки делает главный агент.
- Эти правила действуют во время задачи; они не создают фоновые задачи
  или проверки по расписанию.

## Проверки

- Запускай проверки, соответствующие изменению, по инструкциям компонентов.
  Для изменений бизнес-логики добавляй тесты поведения и регрессий.
- Не добавляй тесты, которые лишь повторяют реализацию; для небольших правок
  текста или CSS достаточно подходящих существующих проверок.
- Для Compose, снимка SQLite и импорта проверь связанные сценарии;
  корневой набор: `python -m unittest discover -s deploy` (требуется Docker).
- Проверяй `git diff --check` в каждом изменённом репозитории.
- Не выдавай пропущенные, закешированные или недоступные проверки за свежий
  успешный запуск. В отчёте укажи результат и непроверенные ограничения,
  включая отсутствие проверки на настоящем iOS/Telegram WebView.

## Документация и версии

- Основная информация о платформе и клубе — в корневом README.
  README компонентов содержат назначение, запуск, проверки и ссылки на детали.
- Сверяй документацию с реализованным поведением и итоговым diff.
  Планы не описывай как готовые функции. Не переписывай несвязанные документы.
- При изменении API обновляй OpenAPI; при изменении настроек — примеры env
  и инструкции запуска; при изменении пользовательского flow — руководства.
- Пользовательские изменения фиксируй в разделе «Не выпущено» CHANGELOG
  соответствующего компонента. Общую историю обновляй для изменений платформы.
  Не присваивай версии и даты релизов без задачи на выпуск.
- Разделяй в планах ближайшие задачи, согласованные отложенные изменения
  и предварительные идеи. Сохраняй утверждённые приоритеты.
- В корневых документах ссылки на файлы сабмодулей ведут в соответствующий
  GitHub-репозиторий, а не в `blob/main/bot/...` основного репозитория.
