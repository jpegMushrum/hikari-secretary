# Архитектура Hikari Secretary

## Слои приложения

`app/bot.py` — композиционный корень. Он создаёт зависимости, подключает доменные
обработчики к `aiogram.Router` и управляет жизненным циклом фонового процесса.
Бизнес-логики в этом модуле быть не должно.

`app/handlers/` содержит входные сценарии Telegram, разделённые по доменам:

- `core.py` — `/start`, `/help` и маршрутизация deep-link;
- `inbox.py` — приоритетная маршрутизация универсального входящего контента;
- `publications.py` — черновики, цели публикации, расписание и медиагруппы;
- `registrations.py` — анкета пользователя, мероприятия, регистрации и посещаемость.

`app/workers/` содержит фоновые процессы. `scheduler.py` забирает из SQLite
готовые к выполнению задания, публикует записи и отправляет напоминания.

`app/runtime.py` хранит явно передаваемые зависимости и только временное состояние
диалогов. Долговечное состояние всегда находится в SQLite, поэтому перезапуск
процесса не теряет очередь, регистрации и напоминания.

`app/access.py` отвечает за общие правила доступа, а `app/presentation.py` — за
чистые функции представления и понятные пользователю тексты ошибок.

`app/db.py` — единая граница хранения данных. Обработчики не выполняют SQL и не
знают структуру таблиц. Изменения схемы вносятся только версионированными
миграциями из `migrations/`.

`app/publishers.py` изолирует API целевых площадок от сценариев создания
публикации.

`app/services/` содержит переиспользуемые прикладные сценарии. В частности,
`PublicationService` является общей точкой создания публикаций для Telegram-
обработчиков и будущих автоматических источников. `DailyTopicService` определяет
контракт генератора ежедневных тем и проверяет результат до постановки в очередь.

`app/repositories/` содержит хранилища отдельных доменов поверх общего соединения
SQLite. `DailyTopicRepository` предоставляет идемпотентную очередь AI-заданий и
историю тем, не раздувая основной класс `Database`.

`app/integrations/` предназначен для адаптеров внешних API. Реализация DeepSeek
должна реализовать `DailyTopicProvider`, не импортируя Telegram-обработчики или
слой хранения.

## Направление зависимостей

```text
main -> bot -> handlers / workers
                  |       |
                  +--- services --- repositories / integrations
                  |       |
                  +--- AppContext --- config / db / Telegram Bot
                  |
                  +--- access / presentation / keyboards / formatting
```

Доменные модули не импортируют композиционный корень и не создают глобальные
экземпляры бота или базы. Это позволяет тестировать их через подмену зависимостей
и добавлять новые домены без изменения существующих сценариев.

## Порядок обработки сообщений

Команды и callback-запросы регистрируются раньше `InboxHandlers`. Входной
маршрутизатор сначала проверяет активный сценарий регистрации или редактирования
профиля и только после этого передаёт сообщение домену публикаций. Там ввод
времени обрабатывается раньше создания нового черновика. Порядок между доменами
закреплён отдельными тестами.

## Добавление нового домена

Для независимой функции следует создать отдельный модуль в `app/handlers/` и,
если ей нужен фоновый цикл, отдельный worker в `app/workers/`. Долговечные данные
добавляются миграцией и методами слоя хранения; временное состояние — отдельной
структурой в `RuntimeState`. В `SecretaryBot` остаются только создание объекта и
одна строка его регистрации.

Все фоновые процессы реализуют `BackgroundWorker`. Композиционный корень запускает
их как независимые задачи, поэтому медленный внешний API не блокирует очередь
публикаций, напоминания и учёт посещаемости.

`DailyTopicWorker` уже реализует обработку, повторные попытки и идемпотентную
постановку результата в публикационную очередь, но не включается в композиционный
корень до появления конкретного AI-провайдера и настроек расписания.

`DeepSeekTopicProvider` использует JSON Output и преобразует внешний ответ в
типизированную `DailyTopic`. В контекст каждого запроса передаётся сохранённая
история разговорных и лексических тем. Сырой ответ модели никогда не передаётся
непосредственно в Telegram.

Сложность конкретной генерации выбирается администратором и хранится во временном
состоянии диалога. `AiTopicSettings` содержит только таргет и настраиваемый через
окружение объём материала.
ИИ-контур связан ровно с одной целью `AI_TOPIC_TARGET_KEY`: сервис ежедневных тем
сам подставляет её при публикации, а `Target.matches()` является общей границей
для будущей фильтрации входящих сообщений по чату и топику Telegram.

`AiTopicHandlers` реализует ручной административный workflow. Уровень JLPT и
комментарий сохраняются в `ai_topic_settings`, поэтому доступны после перезапуска
и используются как ручной, так и автоматической генерацией. Предпросмотр живёт
в `RuntimeState` конкретного администратора и не считается использованной темой.
После подтверждения сервис идемпотентно создаёт публикацию, а репозиторий связывает
её структурированный материал с историей AI-заданий. Перегенерированные и
отменённые предпросмотры в историю не попадают.

`DailyTopicPlannerWorker` идемпотентно поддерживает ближайшее будущее задание и
отдаёт его на генерацию сразу после планирования. Так готовый Rich Message заранее
виден в общей очереди и доступен для просмотра, исправления, перегенерации и отмены.
`DailyTopicWorker` читает актуальные настройки из базы непосредственно перед
запросом к провайдеру и ставит готовую публикацию на заданное время.
