# Структура репозитория и сервисов

Корневой репозиторий `hikari-secretary` — точка сборки всей платформы. Его
`origin` остаётся неизменным. Внутри него будут находиться три Git-сабмодуля:

```text
hikari-secretary/
├── bot/                         # hikari-secretary-bot
├── backend/                     # hikari-secretary-backend
├── miniapp/                     # hikari-secretary-miniapp
├── deploy/                      # production-конфигурация и инструкции
├── docs/                        # общая документация платформы
├── docker-compose.yml           # полный интеграционный стек
├── .github/workflows/           # интеграционный CI/CD
└── .gitmodules
```

Исходный код текущего бота уже перемещён в `bot/`, однако это **ещё не
сабмодуль**: каталог временно отслеживается корневым репозиторием. Перед
`git submodule add` его история будет выделена в отдельный репозиторий
`hikari-secretary-bot`, а обычный каталог заменён Git-сабмодулем. Каталоги
`backend/` и `miniapp/` до подключения соответствующих репозиториев создавать
не нужно: путь сабмодуля должен быть пустым.

## Ответственность компонентов

| Компонент | Репозиторий | Ответственность |
| --- | --- | --- |
| `bot/` | `hikari-secretary-bot` | Python/aiogram, пользовательские Telegram-сценарии, отправка сообщений и доставка задач |
| `backend/` | `hikari-secretary-backend` | Go API, PostgreSQL, миграции, бизнес-правила, outbox и авторизация Mini App |
| `miniapp/` | `hikari-secretary-miniapp` | Интерфейс администраторов внутри Telegram |

После миграции Go-бэкенд станет единственным владельцем PostgreSQL. Бот и Mini
App будут работать с ним через API; прямой доступ к базе из этих компонентов не
допускается.

## Docker Compose

Один `docker-compose.yml` в корне собирает и запускает полный стек:

```text
postgres → backend → bot
                    miniapp
```

В production он будет использовать опубликованные версии образов. Локально он
сможет собирать образы из `./bot`, `./backend` и `./miniapp`.

Не нужно запускать три независимых production Compose-стека: это создаст разные
сети, переменные окружения и неявные зависимости. Отдельные репозитории могут
иметь собственные Dockerfile, тесты и узкий Compose-файл только для локальных
интеграционных тестов — например, backend вместе с временным PostgreSQL.

Текущий корневой `docker-compose.yml` — валидная заглушка. Пока сабмодули не
подключены, обычный `docker compose up` не должен использоваться для deploy.
Профиль `placeholder` существует исключительно, чтобы проверить синтаксис
Compose:

```bash
docker compose --profile placeholder up
```

До выделения `bot/` рабочая конфигурация и SQLite-данные остаются в корне, а
`bot/docker-compose.yml` обращается к ним по умолчанию. Для текущего запуска
используется `docker compose -f bot/docker-compose.yml up -d --build` из корня;
после замены каталога сабмодулем пути будут задаваться интеграционным Compose
или переменными `BOT_ENV_FILE`, `BOT_TARGETS_FILE` и `BOT_DATA_DIR`.

## Порядок перехода

1. Выделить историю каталога `bot/` в репозиторий `hikari-secretary-bot` и
   заменить обычный каталог сабмодулем в том же пути.
2. Создать пустые репозитории `hikari-secretary-backend` и
   `hikari-secretary-miniapp`.
3. Добавить все три репозитория как сабмодули в пути `bot/`, `backend/` и
   `miniapp/`.
4. Заменить заглушку корневого Compose полноценным интеграционным стеком.
5. Добавить CI/CD: проверки сервисов в их репозиториях и интеграционный deploy из
   корня.
