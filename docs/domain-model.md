# Модель данных и перенос первого среза

**Статус:** согласованная модель перед реализацией. Она не является SQL-схемой
и не меняет текущую SQLite-базу.

## Цель первого среза

В PostgreSQL переносятся `People`, `Events`, `Registrations`, `Attendance` и
`Feedback`. Цель — сохранить весь полезный пользовательский и исторический
контекст, но убрать старую техническую связку, где мероприятие идентифицируется
ID публикации SQLite.

Публикации, media, deliveries, AI jobs и временные диалоговые состояния остаются
в SQLite до своих отдельных срезов. Это не двойная запись: после переключения
backend владеет мероприятиями и регистрациями, а SQLite временно владеет только
ещё не перенесёнными публикациями.

## Целевая модель

```text
person ── 1:1 ── telegram_identity
  │
  ├──< event_registration >── event ── 0..1 ── publication_reference
  │          │
  │          └── 0..1 attendance
  │
  └──< feedback >── 0..1 event
```

Новые ключи — `BIGINT GENERATED ... AS IDENTITY`. Безопасность не строится на
непредсказуемости ID: доступ всегда проверяется по роли и принадлежности
объекта.

| Сущность | Важные данные и ограничения |
| --- | --- |
| `people` | ФИО, гражданство РФ, статус студента ИТМО, `feedback_offers_enabled`, timestamps. |
| `telegram_identities` | `telegram_user_id BIGINT UNIQUE`, ссылка на человека, актуальные username и display name, `last_seen_at`. Username допускает `NULL`; отображаемое имя остаётся fallback. |
| `events` | Название, `starts_at`, `ends_at`, состояние `active/cancelled/completed`, автор, timestamps. Проверка `starts_at < ends_at`; лимит пяти активных событий обеспечивается use case и конкурентно-безопасной операцией. |
| `event_publication_references` | Необязательная связь мероприятия с публикацией. В первом переходе может содержать legacy SQLite `post_id`, но он не является primary key мероприятия. |
| `event_registrations` | Уникальная пара `event_id + person_id`, состояние `registered/cancelled`, время регистрации и отмены, признак и выбранное смещение напоминания, отметки отправки напоминания и вопроса о посещении. |
| `attendance` | Одна запись на регистрацию: `attended`, время запроса и время ответа. Отсутствие записи означает, что ответ ещё не получен. |
| `feedback` | Автор, текст, время и необязательный `event_id`. `NULL event_id` обозначает общий отзыв. |
| `outbox` | Неразрушаемая заявка на внешнее действие: уведомление, напоминание или запрос посещения. Записывается в одной транзакции с изменением состояния. |
| `audit_log` | Актор, действие, объект, timestamp и idempotency key; не используется как источник бизнес-состояния. |

Роль администратора после появления постоянной модели хранится в `access`
модуле. До этого `ADMIN_TELEGRAM_IDS` остаётся bootstrap allowlist: он нужен,
чтобы первый администратор мог безопасно управлять ролями в новой базе.

## Отображение текущих SQLite-данных

| SQLite | PostgreSQL | Правило переноса |
| --- | --- | --- |
| `user_profiles` | `people` + `telegram_identities` | `full_name` — единственное имя; username/display name переносятся как последние известные значения; настройка отзывов сохраняется. |
| `events` | `events` + `event_publication_references` | Создаётся собственный ID события; `post_id` сохраняется только в таблице ссылки. Заголовок, время, статус и отмена переносятся без изменения смысла. |
| `registrations` | `event_registrations` + `attendance` | Сохраняются статусы, времена регистрации/отмены, reminder offset и отметки доставки; `attended` и время ответа переносятся в attendance. |
| `feedback_entries` | `feedback` | `post_id` сопоставляется с новым событием через import map; пустая ссылка остаётся общим отзывом. |
| `registration_flows`, `profile_edit_flows`, `feedback_flows` | не переносятся | Это незавершённые UI-диалоги. Во время cutover пользователь начинает их заново. |
| `posts`, `media`, `deliveries` | не входят в первый срез | Остаются владельчеством SQLite до среза Publishing. |
| `ai_topic_jobs`, `ai_topic_settings` | не входят в первый срез | Будут перенесены в Learning Content вместе с историей материалов. |

Импортёр ведёт отдельную таблицу `legacy_import_map`: тип исходной записи,
SQLite ID и новый PostgreSQL ID. Она позволяет сверить перенос и восстановить
связи, но не участвует в доменных правилах.

## Переход состояния

```text
SQLite active (только до окна cutover)
  → backup SQLite
  → dry-run import + отчёт сверки
  → короткая остановка bot
  → финальный import в одной версии схемы
  → проверить counts и инварианты
  → включить Bot API для первого среза
  → backend становится владельцем People/Events/Feedback
```

Нельзя одновременно продолжать писать мероприятие или регистрацию в обе базы.
Если проверка не проходит, bot остаётся на прежней версии с SQLite, а новый
PostgreSQL-том удаляется или помечается как неиспользованный. Исходная SQLite
резервная копия никогда не удаляется импортёром.

## Критерии успешного импорта

1. Количество профилей, событий, регистраций и отзывов совпадает с ожидаемым
   количеством или каждая исключённая запись объяснена в отчёте.
2. У каждого перенесённого события есть корректные время начала и окончания;
   у регистрации есть существующие person и event.
3. Все связанные отзывы ведут на перенесённое событие; общие отзывы остаются
   общими.
4. Повторный запуск import в dry-run не создаёт дубликаты.
5. Тестовая копия SQLite проходит импорт до production cutover.
6. Включённый bot использует только закрытый Bot API для перенесённых use
   cases и не открывает SQLite-таблицы этих доменов.

## Состояние реализации

SQL-миграция `000002_people_events_feedback` создаёт целевые таблицы первого
среза и `legacy_import_map`. В backend уже реализованы сервисная
аутентификация bot-to-backend, синхронизация Telegram-идентичности (`PPL-01`)
и защищённая административная read-модель людей (`STATS-01`).

До production cutover остаются use cases профиля, мероприятий, регистраций,
посещаемости и отзывов, транзакционный outbox и importer в режиме dry-run.
Наличие таблиц само по себе ещё не передаёт владение данными от SQLite
backend-сервису.
