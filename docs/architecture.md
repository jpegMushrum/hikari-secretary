# Целевая архитектура Hikari Secretary

**Статус:** согласована 2026-10-28. Документ описывает целевое состояние
платформы; работающий Python-бот `v0.9.0` пока остаётся самостоятельной
реализацией на SQLite.

## Решения

- Платформа поддерживает только **Telegram**. VK не является частью продукта,
  не имеет publisher, конфигурации или миграционного пути.
- Backend — модульный монолит на Go с прагматичными принципами Clean/Hexagonal
  Architecture, а не набор микросервисов.
- PostgreSQL станет единственным источником бизнес-данных. Bot и Mini App не
  получают прямой доступ к базе.
- Python-бот сохраняет роль Telegram-адаптера и delivery worker: он принимает
  Telegram updates, показывает привычный участникам интерфейс и доставляет
  задания в Telegram. Бизнес-правила постепенно переезжают в backend.
- Mini App — административный интерфейс backend. Его интерфейс не дублирует
  бизнес-логику бота.
- Перенос выполняется вертикальными срезами. У каждого перенесённого домена
  бывает ровно один владелец данных; постоянная двойная запись в SQLite и
  PostgreSQL запрещена.

## Контекст системы

```text
Участник ── Telegram ──> Python bot ── service token ──> Go backend
                                                        │
Администратор ── Telegram Mini App ── initData ────────┤
                                                        v
                                                   PostgreSQL
                                                        │
                         outbox / schedule <───────────┘
                                                        v
                                           Python delivery worker
                                                        │
                                                        v
                                                    Telegram
```

Backend создаёт и хранит бизнес-состояние. Delivery worker получает готовое
задание, отправляет его в Telegram и подтверждает результат; он не решает,
какой материал, когда и кому нужно отправить.

## Границы доступа

| Вход | Аутентификация | Права | Состояние |
| --- | --- | --- | --- |
| `GET /healthz`, `GET /readyz` | нет | только служебный статус | реализовано |
| `/api/v1/admin/**` | исходная `Telegram.WebApp.initData` | роль администратора | проверка `initData` и allowlist реализованы |
| `/internal/bot/v1/**` | отдельный `BOT_SERVICE_TOKEN` | только операции бота | будет добавлено до переноса первого домена |

`initData` доказывает личность пользователя Telegram, но не подходит для
межсервисного взаимодействия: бот не является Mini App-пользователем. Поэтому
токен bot-to-backend будет отдельным случайным секретом, не токеном Telegram
бота. В production внутренние маршруты дополнительно не публикуются reverse
proxy наружу.

## Модули backend

| Модуль | Ответственность | Не отвечает за |
| --- | --- | --- |
| Identity & Access | Telegram-идентичности, админские роли, сервисные credentials | профиль участника и мероприятия |
| People | профиль участника, отображаемое Telegram-имя, настройки отзывов | права администратора |
| Events | мероприятия, регистрации, напоминания, посещаемость, список участников | формат и доставка публикации |
| Feedback | связанные с мероприятием и общие отзывы | решение, кого спросить о посещении |
| Publishing | черновики, очередь, публикационные цели Telegram, outbox доставки | генерация учебного содержания |
| Learning Content | материалы разговорного клуба, версии, история, генерация, правила ежедневного создания | отправка сообщения в Telegram |
| Language Practice | будущая проверка японского языка только в заданном чате и топике | генерация материалов |

`Language Practice` — запланированный модуль, его реализация пока не входит в
первый перенос.

### Материалы разговорного клуба

Термин «AI-материалы» заменяется на **«Материалы разговорного клуба»**. AI —
внешний способ подготовить черновик, а не домен продукта.

Модуль хранит структурированный материал: тему, вопросы, лексику, грамматику,
JLPT-уровень, версию, историю и статус. Внешний DeepSeek-адаптер реализует
порт генератора. После одобрения либо автоматической валидации модуль создаёт
заявку в `Publishing`; прямой отправки в Telegram у него нет.

Для ежедневной политики предусмотрены два режима:

- `manual_review` — сгенерированный материал ждёт администратора;
- `auto_publish` — валидный материал автоматически передаётся в очередь.

Задание генерации не создаёт публикацию, пока материал не прошёл структурную
валидацию. Ошибка, включая усечённый ответ модели, остаётся ошибкой задания и
не создаёт пустой пост.

## Слои и зависимости

```text
adapters (HTTP Mini App, Bot API, scheduler, PostgreSQL, DeepSeek, Telegram)
                                ↓
application (use cases, транзакции, порты)
                                ↓
domain (сущности, инварианты, переходы состояний)
```

Внешние технологии не проникают в domain: там нет типов `net/http`, `pgx`,
aiogram или SDK AI-провайдера. `cmd/api` остаётся composition root, где вручную
собираются зависимости.

Интерфейсы вводятся только на реальных границах: репозитории, транзакции,
outbox, часы и внешние клиенты. Простые структуры и запросы не получают
искусственных слоёв или DI-фреймворка.

## Запросы таблиц Mini App

Административные read-модели используют offset pagination с явным номером
страницы: объём одной страницы ограничен вариантами `10`, `20` и `30`. Такой
контракт соответствует таблицам Mini App, где администратору важны номер
страницы и общее число записей. Смена фильтра, сортировки или page size всегда
начинает выборку с первой страницы.

API получает типизированные query-параметры, а application layer сопоставляет
их с конечным allowlist полей фильтрации и сортировки конкретной read-модели.
Никакие SQL-выражения, имена колонок или произвольные условия от клиента не
принимаются. Каждая сортировка завершается стабильным `id`, а PostgreSQL-индексы
добавляются вместе с новыми часто используемыми фильтрами.

Этот read-контракт применяется ко всем административным спискам: людям,
мероприятиям, участникам, отзывам и позднее публикациям. Он не относится к
небольшим пользовательским спискам Telegram-бота, для которых пагинация может
иметь другие UX-правила.

## Организация кода

```text
backend/
├── cmd/
│   ├── api/                         # composition root HTTP API
│   └── migrate/                     # SQL migrations
├── internal/
│   ├── platform/                    # config, auth, postgres, migrations, HTTP infra
│   ├── modules/
│   │   ├── people/
│   │   │   ├── domain/
│   │   │   ├── application/
│   │   │   └── adapters/postgres/
│   │   ├── events/
│   │   ├── feedback/
│   │   ├── publishing/
│   │   └── learningcontent/
│   └── adapters/
│       ├── miniapp/                 # admin HTTP controllers
│       ├── botapi/                  # internal Bot API controllers
│       └── workers/                 # scheduler and outbox workers
└── migrations/                       # единый упорядоченный SQL-журнал
```

Миграции остаются одним последовательным журналом, но имя миграции должно
показывать владельца: например, `000002_people.sql` или
`000003_events.sql`.

## Гарантии доставки и аудит

Команда, которая меняет важное состояние и требует внешнего действия,
записывает его в одной транзакции с записью `outbox`. Например, регистрация
может породить напоминание, отмена мероприятия — уведомления участникам,
одобренный материал — публикационную задачу. Воркер подтверждает обработку
идемпотентно; повторная доставка не должна создавать второй пост или второе
уведомление.

Изменения администраторов и служебные действия бота получают аудит: актор,
время, действие, объект и идемпотентный ключ, когда он есть.

## Порядок переноса

Первый вертикальный срез: `People + Events + Registrations + Attendance +
Feedback`. Он даёт ценность участникам и будущей административной панели, но
не вынуждает сразу переносить медиа и публикационный delivery.

Второй срез: `Publishing` и outbox доставки только в Telegram. Третий:
`Learning Content`, включая импорт истории AI-материалов. Каждый срез имеет
резервную копию, одноразовый импорт, сверку и контролируемое переключение
бота на backend API.

Подробная целевая модель первого среза и порядок миграции описаны в
[модели данных и плане переноса](domain-model.md).
